# Руководство для LLM: редактирование (цензурирование) JSON-дампа Ramus RSF

Этот документ написан **для LLM** (или для человека, пишущего для неё
сценарий), которой передан JSON-файл, полученный из функции дампа/
экспорта этого приложения, с просьбой отредактировать или иным образом
отцензурировать конфиденциальный текст в нём так, чтобы результат можно
было импортировать обратно и сохранить как рабочий файл `.rsf`. Если вы —
LLM, выполняющая эту задачу, прочитайте весь документ, прежде чем
редактировать что-либо.

JSON получен из `dump_model()` (`ramus_rsf_tool/rsf_model.py`) одним из
двух способов:

- через **вкладку «Атрибуты» / «JSON-дамп» → Экспорт в файл…** в GUI, или
- через `ramus-rsf-cli dump FILE.rsf [--all] [--pretty]`

...и возвращается обратно одним из двух способов:

- через **вкладку «JSON-дамп» → Импорт из файла…** (или **Применить
  отредактированный текст ниже**, если вы редактируете прямо в
  приложении) в GUI, или
- через `ramus-rsf-cli import-json FILE.rsf dump.json OUT.rsf`

Оба пути импорта вызывают одну и ту же функцию, `apply_json_dump()`, и эта
функция — **патч**, а не полный импорт/замена. Понимание того, что именно
она делает и чего не делает — вся суть этого руководства: ошибётесь, и
ваши правки либо будут молча пропущены (раздражает, но безопасно), либо, в
одном конкретном случае, разобранном ниже, приведут к файлу, который
больше не отражает то, что вы намеревались сделать.

## 1. Самое важное правило

> **Изменение значения в JSON изменяет это значение. Удаление или
> пропуск блока *ничего не делает* — оно не удаляет соответствующий
> квалификатор или элемент из файла.**

Если ваша задача — «отцензурировать конфиденциальную информацию»,
правильное действие для конфиденциального поля — **перезаписать его
значение** (например, на `"[УДАЛЕНО]"`), но никогда не удалять окружающий
его блок JSON. `apply_json_dump()` патчит только те квалификаторы/
элементы, которые присутствуют **и** в файле, **и** в вашем JSON,
сопоставленные по числовому `id`. Всё, что есть в файле, но отсутствует в
вашем JSON — потому что вы это удалили, или потому что дамп был снят с
исключёнными системными квалификаторами — остаётся полностью нетронутым.
В этом рабочем процессе вообще нет операции удаления.

Это также означает: **никогда не придумывайте новые значения `id` и не
добавляйте новые блоки квалификатора/элемента/атрибута, которых не было в
исходном дампе.** Они будут искаться по id, не будут найдены и будут
молча пропущены (об этом сообщается как о предупреждении, а не как об
ошибке, но в сохранённый файл они всё равно не попадут).

## 2. Форма JSON

```json
{
  "qualifiers": [
    {
      "id": 9,
      "name": "Enterprise activity",
      "system": false,
      "elements": [
        {
          "id": 80,
          "name": "Administrative processes",
          "attributes": {
            "Name": "Administrative processes",
            "F_BOUNDS": {"X": 40.0, "Y": 40.0, "WIDTH": 140.0, "HEIGHT": 80.0},
            "F_BACKGROUND": -16711936,
            "F_FOREGROUND": -16777216,
            "F_FONT": {"NAME": "Dialog", "STYLE": 0, "SIZE": 12},
            "F_STATUS": {"TYPE": 0, "OTHER_NAME": "reviewed by J. Smith, ext. 4471"},
            "F_TYPE": 3,
            "F_AUTHOR": "J. Smith"
          }
        }
      ]
    }
  ]
}
```

- **Верхний уровень**: один объект с одним ключом, `"qualifiers"` —
  список. Именно эта обёртка обязательна; и `apply_json_dump()`, и импорт
  в GUI отклоняют всё, что не является `{"qualifiers": [...]}` на верхнем
  уровне.
- **Квалификатор** (`"id"`, `"name"`, `"system"`, `"elements"`): примерно
  «класс» — одна страница диаграммы IDEF0 либо одна из встроенных
  системных таблиц приложения. `id` — ключ соединения; `name` — его
  отображаемое имя (редактируемо — см. §3); `system` — только
  информационное поле, его изменение ни на что не влияет.
- **Элемент** (`"id"`, `"name"`, `"attributes"`): «экземпляр» своего
  квалификатора — функциональный блок на диаграмме, или строка в какой-то
  другой таблице. `id` — ключ соединения; `name` зеркалирует внутреннее
  поле файла `ELEMENT_NAME` (редактируемо — см. §3); `attributes` —
  словарь всех значений, установленных сейчас на этом элементе.
- **Запись атрибута**: ключ = имя атрибута (например, `"Name"`,
  `"F_BOUNDS"`), либо `"attr_<N>"`, если у него нет имени. Форма значения
  зависит от типа атрибута — это как раз та часть, с которой нужно быть
  осторожнее, и она разбирается далее.

В дампе присутствуют только те квалификаторы/элементы/атрибуты, у которых
действительно есть установленное значение — ничего не дополняется
пустыми записями или null-значениями «для порядка».

## 3. Что можно безопасно редактировать — и что произойдёт, если вы этого не сделаете

| Место в JSON | Можно ли редактировать? | Эффект при изменении |
|---|---|---|
| `qualifiers[].id`, `elements[].id` | **Нет — никогда** | Это единственный способ, которым правки сопоставляются с нужным местом в файле. Измените id — и ваша правка (и каждый атрибут под ней) будет молча пропущена как «не найдено». |
| `qualifiers[].name` | Да | Переименовывает квалификатор (например, заголовок страницы диаграммы). |
| `qualifiers[].system` | Нет эффекта в любом случае | Только для чтения; игнорируется при импорте. |
| `elements[].name` | Да | Переименовывает элемент (отражается в колонке `ELEMENT_NAME` файла, а также в атрибуте `Name`, если он есть у этого квалификатора — отдельно редактировать `attributes.Name` не обязательно, хотя это тоже допустимо и, если присутствуют оба варианта, имеет приоритет). |
| `attributes.<X>`, где значение — **обычная строка** | **Да — это почти всегда то, что вы цензурируете** | например, `"Name"`, `F_AUTHOR`, `F_STATUS.OTHER_NAME`, `F_PROJECT_PREFERENCES.DEFINITION`/`PROJECT_AUTOR`, текст формулы и т.д. |
| `attributes.<X>`, где значение — **число или логическое значение** | Технически да, но не делайте этого без конкретной причины | Позиции, размеры, цвета (упакованные знаковые целые, а не RGB-тройки — см. §5), размер/стиль шрифта, коды статуса/типа. Цензурирование текста никогда не должно требовать правки этих полей. |
| `attributes.<X>`, где значение — **объект** (атрибут в режиме `struct`, например `F_BOUNDS`, `F_FONT`, `F_STATUS`, `F_PROJECT_PREFERENCES`) | Редактируйте отдельные строковые поля внутри него | Можно вернуть частичный объект только с изменённым(и) полем(ями), либо весь объект без изменений, кроме вашей правки — работает и так, и так, поскольку импорт объединяет по полям. |
| `attributes.<X>`, где значение — **массив объектов** (атрибут в режиме `list`) | **Нет — всегда игнорируется** | например, атрибуты-ссылки/иерархические/списки элементов. Они показываются в дампе для наглядности, но импорт их никогда не трогает (об этом выдаётся предупреждение, но правка не применяется). Если что-то из этого нужно отцензурировать, это нужно делать через вкладку «Сырые таблицы» приложения, а не через этот JSON-процесс. |
| `attributes.<X>`, равное `{"__bytes_len__": N}` | **Нет — всегда игнорируется, и цензурировать здесь и так нечего** | Это заглушка для бинарного/файлового/форматированного текстового содержимого (значки, вложения, HTML-поле `Description`, кэшированные данные отрисовки). **Дамп никогда не содержит сами байты/текст**, только их длину, поэтому если конфиденциальный контент находится в одном из таких полей, этот JSON-процесс не может его увидеть или отцензурировать — вам нужно отметить это для пользователя, чтобы он обработал отдельно (в редакторе атрибутов GUI есть кнопка «Редактировать как текст…» специально для полей `Description`/HTML). Никогда не удаляйте эту заглушку-ключ, думая, что это очистит поле — это ничего не делает. |
| Атрибут просто **отсутствует** в `attributes` | Н/П | Означает, что у него нет установленного значения в файле. Не добавляйте его — новые ключи импортом не создаются. |

## 4. Дисциплина типов

`apply_json_dump()` сравнивает новое значение с текущим простой проверкой
на равенство и записывает его обратно, используя тот же тип, что вы
задали. Чтобы избежать предупреждений или, что хуже, записи в файл
значения неверного вида:

- **Сохраняйте тип JSON в точности таким, каким вы его нашли.** Число
  остаётся числом JSON (`12`, `40.0`), а не строкой в кавычках (`"12"`).
  Логическое значение остаётся `true`/`false`, а не `"true"`. Только
  строки должны становиться другими строками.
- **Не переформатируйте числа, которые не меняете** (например, не
  превращайте `40.0` в `40` или `40.00`) — это не нужно, а в поле
  `struct` может вызвать ложную запись «значение изменилось» для поля,
  которое вы трогать не собирались. Самая простая и безопасная политика:
  **переписывайте только те точные подстроки/значения, которые вы
  цензурируете; остальные байты JSON оставляйте как есть.**
- **Никогда не меняйте имя ключа** (`"Name"` должно оставаться `"Name"`,
  `"attr_42"` должно оставаться `"attr_42"` — последнее кодирует id
  атрибута, а не произвольную метку).
- **Результат должен быть синтаксически корректным JSON.** Он разбирается
  строго (`json.loads`); лишняя запятая или неэкранированная кавычка
  приведёт к провалу всего импорта, ничего не будет применено.

## 5. Что выглядит «похожим на конфиденциальное», но не является текстом для цензурирования

- **Цвета** (`F_BACKGROUND`, `F_FOREGROUND`, любой атрибут `IDEF0.Color`):
  одно знаковое 32-битное целое (упакованный ARGB, например `-16711936` =
  непрозрачный зелёный), а не строка RGB. Не трогайте эти числа.
- **Позиции/размеры** (`F_BOUNDS.X/Y/WIDTH/HEIGHT`): числа с плавающей
  точкой, только геометрия.
- **Коды статуса/типа** (`F_STATUS.TYPE`, `F_TYPE`, `F_FONT.STYLE`):
  небольшие целые с фиксированными значениями (см. `RAMUS_RSF_FORMAT.md`
  §8), а не произвольные данные.
- **Ключи `attr_<N>`**: `<N>` — числовой id атрибута, а не значение для
  цензурирования — оставляйте текст самого ключа нетронутым, редактируйте
  только его значение (если это значение само по себе является строкой,
  которую нужно отцензурировать).

## 6. Шпаргалка по форме атрибутов

Что вы увидите в дампе, в зависимости от режима хранения атрибута
(`rsf_model.TYPE_MAP`), и будет ли импорт реагировать на вашу правку:

| Режим | Выглядит в JSON как | Редактируется через этот процесс? |
|---|---|---|
| `scalar` | Обычная строка / число / логическое значение | Да (если это строка, которую вы цензурируете) |
| `struct` | Объект JSON вида `{COLUMN: value}` | Да, по каждому строковому полю внутри него |
| `list` | Массив JSON из объектов-строк | **Нет, всегда игнорируется** |
| `stream` (файл/HTML-текст) | `{"__bytes_len__": N}`, либо отсутствует, если не задано | **Нет, всегда игнорируется** — реального содержимого в дампе нет |
| любое значение, которое оказывается бинарным, даже внутри в остальном редактируемого атрибута `scalar`/`struct` (например, байты изображения значка) | `{"__bytes_len__": N}` в этом месте | **Нет, всегда игнорируется** — остальные строковые поля в том же struct по-прежнему редактируемы |
| тип атрибута, у которого вообще нет записи в `TYPE_MAP` (например, часть внутренней механики стрелок/секторов) | **Вообще не появляется в дампе** | Н/П — невидим для этого процесса; используйте вкладку «Сырые таблицы» в GUI |

## 7. Разобранный пример

**Вход** (`dump.json`, один элемент с несколькими видами конфиденциального
текста):

```json
{
  "qualifiers": [
    {
      "id": 9,
      "name": "Enterprise activity",
      "system": false,
      "elements": [
        {
          "id": 80,
          "name": "Alice Johnson - Account Review",
          "attributes": {
            "Name": "Alice Johnson - Account Review",
            "F_AUTHOR": "alice.johnson@example.com",
            "F_BOUNDS": {"X": 40.0, "Y": 40.0, "WIDTH": 140.0, "HEIGHT": 80.0},
            "F_BACKGROUND": -16711936,
            "F_STATUS": {"TYPE": 0, "OTHER_NAME": "approved by phone, SSN on file 123-45-6789"},
            "F_TYPE": 3
          }
        }
      ]
    }
  ]
}
```

**Правильное цензурирование** — изменены только строковые значения, всё
остальное (id, числа, структура, ключи) побайтово идентично:

```json
{
  "qualifiers": [
    {
      "id": 9,
      "name": "Enterprise activity",
      "system": false,
      "elements": [
        {
          "id": 80,
          "name": "[УДАЛЕНО ИМЯ] - Account Review",
          "attributes": {
            "Name": "[УДАЛЕНО ИМЯ] - Account Review",
            "F_AUTHOR": "[УДАЛЕН EMAIL]",
            "F_BOUNDS": {"X": 40.0, "Y": 40.0, "WIDTH": 140.0, "HEIGHT": 80.0},
            "F_BACKGROUND": -16711936,
            "F_STATUS": {"TYPE": 0, "OTHER_NAME": "approved by phone, [УДАЛЁН СНИЛС/ПАСПОРТ]"},
            "F_TYPE": 3
          }
        }
      ]
    }
  ]
}
```

Применение этого патчит ровно два значения атрибутов плюс имя элемента
(`Name` дедуплицируется с верхнеуровневым `name` автоматически, так что
это считается как `Name` + `F_AUTHOR` + `F_STATUS` = 3 обновлённых
значения на 1 элементе — см. правило из §1 про `name` в сравнении с
`attributes.Name`), и сообщает о нуле предупреждений.

**Что пошло бы не так при наивном подходе** — удаление элемента вместо
цензурирования его полей:

```json
{ "qualifiers": [ { "id": 9, "name": "Enterprise activity", "system": false, "elements": [] } ] }
```

Это **не** удаляет элемент 80 из файла. Элемент 80, со всем своим
исходным нецензурированным текстом, остаётся точно таким же, каким был —
импорту просто нечего сказать про id, о котором ему не сообщили. Если
целью было стереть данные Алисы из файла, этот способ оставляет их
полностью нетронутыми. Используйте первый вариант.

## 8. Чек-лист перед тем, как вернуть отцензурированный JSON

- [ ] Результат — валидный JSON, та же верхнеуровневая форма
      `{"qualifiers": [...]}`.
- [ ] Ни одно поле `id` нигде не было изменено.
- [ ] Ни один блок квалификатора/элемента/атрибута не был добавлен или
      удалён — изменены только значения внутри существующих блоков.
- [ ] Были переписаны только строковые значения; каждое число, логическое
      значение и заглушка `{"__bytes_len__": ...}` нетронуты, вплоть до
      точного типа.
- [ ] Флаги `"system"`, массивы в режиме `list` и всё под заглушкой
      `{"__bytes_len__": ...}` оставлены без изменений (сообщите об этом
      пользователю отдельно, если там есть что-то, что нужно
      отцензурировать — этот процесс не может до этого добраться).
- [ ] Имена ключей (`"Name"`, `"F_BOUNDS"`, `"attr_42"` и т. д.) не
      изменены.
- [ ] Ничего сверх того, о чём вас реально попросили отцензурировать, не
      было изменено — более точечный, хирургический diff легче для
      доверия пользователя и легче перезапустить при необходимости
      корректировки.

## 9. Передача результата обратно

Скажите пользователю выполнить повторный импорт одним из способов:

```sh
ramus-rsf-cli import-json ORIGINAL.rsf redacted-dump.json OUTPUT.rsf
```

либо в GUI: **вкладка «JSON-дамп» → Импорт из файла…** (выбрать
отцензурированный JSON-файл), а затем **Файл → Сохранить как…**. Любой из
путей выдаёт сводку — количество изменений, плюс предупреждения по
записям, которые не удалось применить (неверный/неизвестный id, атрибут
типа list/stream, несовпадение типов) — стоит передать это пользователю,
чтобы он убедился, что ничего из ожидаемых изменений не было молча
пропущено.
